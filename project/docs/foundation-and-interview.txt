STEP 3 — PostgreSQL + Prisma
Goal:
Create the relational data foundation.

Initial models:
- User
- Resume
- Interview
- Question
- Answer
- Evaluation
- UsageLimit (per-user daily/monthly AI usage caps — see Step 7)
- AIUsage (per-request record: userId, provider, model, requestType, promptVersion, inputTokens, outputTokens, estimatedCost, latency, cacheHit, retryCount, status, failureCategory, createdAt — populated starting Step 7, needed for both usage-cap enforcement and cost observability in Step 13)
- PromptVersion (id, task, version label, model, provider, createdAt — referenced by AIUsage and by evaluation records so every AI call can be traced back to the exact prompt that produced it)
- EvalRun (id, triggeredBy, promptVersionId, datasetVersion, startedAt, completedAt, passFail, summaryMetrics — one row per execution of the golden-set regression suite in Step 14)
- EvalResult (id, evalRunId, goldenSetItemId, actualScore, expectedScoreRange, conceptsMatched, judgeScore, pass/fail — one row per golden-set item within an EvalRun)

Important relationships:
User → Interview
Interview → Question
Question → Answer
Answer → Evaluation
User → UsageLimit
User → Resume (cascade delete: deleting a resume or account must cascade to resume-derived data added in Step 11 — chunks and embeddings)
User → AIUsage
PromptVersion → AIUsage
PromptVersion → Evaluation (which prompt version produced a given evaluation)
EvalRun → EvalResult (one-to-many)
PromptVersion → EvalRun

Note:
These four models (AIUsage, PromptVersion, EvalRun, EvalResult) are created here in the foundation step, even though nothing writes to them until Step 7 (AIUsage), Step 8 (prompt-version tagging on Evaluation), and Step 14 (EvalRun/EvalResult) — this avoids a schema migration mid-build once usage tracking and evals are implemented.

Add:
- Primary keys
- Foreign keys
- Created/updated timestamps
- Useful indexes
- Cascade rules where appropriate (required for resume deletion, not optional — see Step 10)

Deliverable:
- PostgreSQL connected.
- Prisma schema created.
- Initial migration applied.
- Prisma client available to backend services.


STEP 4 — Authentication + authorization
Goal:
Secure private application resources.

Implement:
- Signup/login/logout through the selected auth solution.
- Protected dashboard.
- Auth middleware.
- Current-user endpoint.
- Object-level authorization.

Rules:
- User A must never access User B's resume.
- User A must never access User B's interview.
- User A must never access User B's answers/evaluations.

Deliverable:
- Protected routes work.
- Unauthorized requests return appropriate errors.
- Ownership checks are implemented at service/controller boundaries.


STEP 5 — Interview setup
Goal:
Allow users to create a mock interview.

Interview configuration:
- Role
- Experience level
- Interview type
- Difficulty
- Number of questions

Example roles:
- Frontend Developer
- Backend Developer
- Full Stack Developer
- Software Engineer
- Data Analyst
- QA Engineer

Create:
POST /api/interviews

Store:
- userId
- role
- experienceLevel
- interviewType
- difficulty
- questionLimit
- status

Note:
Interview creation should be checked against the user's UsageLimit (daily/monthly cap) in addition to the per-hour rate limit — the cap enforcement itself is implemented in Step 7, but the interview creation endpoint is one of the checkpoints that calls it.

Deliverable:
User can create and view an interview configuration.
