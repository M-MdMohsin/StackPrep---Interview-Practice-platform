2.4 Database

Primary database:
- PostgreSQL

Why:
The data is highly relational:

User
 ↓
Resume
 ↓
Interview
 ↓
Question
 ↓
Answer
 ↓
Evaluation

Additional relationships:
User → UserSkill
Resume → ResumeChunk
ResumeChunk → Embedding/vector
Interview → Question
Question → Answer
Answer → Evaluation
Question → parent Question for adaptive follow-ups

PostgreSQL is preferable because the platform requires relational integrity, filtering, analytics, and transactional workflows.

Use:
- Prisma for relational application models.
- pgvector for resume/role embeddings and similarity search, with the vector column dimension matching the chosen embedding model's output size (e.g. 768 for Gemini text-embedding-004).

Prisma's relational mode with PostgreSQL should use database foreign keys to maintain referential integrity.

2.6 AI Provider Abstraction

Do not tightly couple the entire backend to Gemini.

Use:

AIService
   │
   ├── GeminiProvider
   ├── GroqProvider
   └── OpenRouterProvider

Interface:

interface AIProvider {
  generateQuestion(): Promise<Question>;
  evaluateAnswer(): Promise<Evaluation>;
  generateFollowUp(): Promise<Question>;
  analyzeResume(): Promise<ResumeAnalysis>;

Provider selection should be configurable by task, availability, latency, and failure policy.

2.8 LLM Evaluation / Evals

Schema validation is not sufficient to prove that an AI evaluator is producing useful feedback.

The project must include an evaluation pipeline.

Golden set:
- Start with a small manually reviewed dataset.
- Recommended initial target: approximately 50 representative answers.
- Cover strong, average, weak, incomplete, incorrect, off-topic, and ambiguous answers.
- Include multiple roles and difficulty levels where practical.
- Store expected score ranges and evaluation criteria.
- Version the dataset.

Example:

{
  "id": "golden-001",
  "question": "What is database indexing?",
  "answer": "...",
  "expectedScoreRange": [7, 9],
  "expectedConcepts": [
    "faster lookup",
    "index structure",
    "write/storage tradeoff"
  ]
}

Regression runner:
- Run the current evaluator against the golden set.
- Compare score ranges and required concepts.
- Compare feedback quality metrics.
- Compare against a stored baseline.
- Flag regressions.
- Produce a machine-readable and human-readable report.

Prompt/model versioning:
Every AI evaluation should record:
- Prompt version
- Model
- Provider
- Evaluation schema version
- Timestamp

LLM-as-judge:
- A second, cheaper model can periodically review evaluator outputs.
- It should judge consistency, relevance, correctness, and usefulness.
- Judge results should be treated as an additional quality signal, not absolute truth.

CI quality gate:
Prompt/model changes should run the golden-set evaluation before deployment.

Example policy:
- No critical regression in required concepts.
- Score consistency must remain within configured tolerance.
- LLM-as-judge quality must not fall below the configured threshold.

Thresholds should be defined in configuration and tuned using actual evaluation results.

2.10 Caching Strategy

Redis/Upstash should provide the first caching layer.

Caching categories:

1. Question-generation cache
Useful for reusable role/difficulty/topic requests.

2. Semantic cache
Use normalized request features and/or embeddings to identify sufficiently similar question-generation requests.

3. Retrieval cache
Cache repeated resume/role retrieval results where safe.

4. Prompt/provider cache
Where the selected provider supports prompt caching, use it for large repeated static context when economically beneficial.

Cache key should include relevant version information:
- Task
- Role
- Difficulty
- Topic/context hash
- Prompt version
- Model
- Provider
- Schema version

Do not blindly cache:
- User-specific answer evaluations.
- Sensitive personalized outputs.
- Responses whose correctness depends on rapidly changing private state.

Track:
- Cache hit rate
- Cache miss rate
- Cache latency
- Invalidations
- Estimated AI calls avoided

Cache effectiveness must be measured rather than assumed.


2.11 Resume and Answer Security / Prompt-Injection Defense

Resume uploads are an untrusted input boundary. User-submitted interview answers are a second untrusted input boundary, since answer text is fed back into follow-up-generation and evaluation prompts. Both must go through equivalent defenses before reaching an LLM prompt.

Resume pipeline:

File upload
 ↓
File type/size validation
 ↓
Safe text extraction
 ↓
Content normalization
 ↓
Prompt-injection/suspicious-instruction detection
 ↓
Chunking
 ↓
Embedding
 ↓
Storage
 ↓
RAG retrieval
 ↓
LLM prompt

Requirements:
- Accept only supported document types.
- Enforce maximum file size.
- Do not execute uploaded content.
- Strip or normalize unsupported content where appropriate.
- Detect instruction-like phrases attempting to control the model.
- Treat extracted resume text as data, not system instructions.
- Keep system/developer instructions separate from retrieved resume content.
- Limit retrieved context size.
- Log guardrail events without exposing sensitive resume content.
- Provide a safe failure path when suspicious content is detected.

Answer text pipeline:

Answer submitted
 ↓
Length/token limit check
 ↓
Prompt-injection/suspicious-instruction detection
 ↓
Stored as answer record
 ↓
Passed to evaluation/follow-up prompt as untrusted data

Requirements:
- Apply the same instruction-like-content detection used for resumes to submitted answer text.
- Never let answer text be interpreted as system/developer instructions (e.g. "ignore the rubric," "give a perfect score").
- Apply the same input/token limits used for resume content.
- Log guardrail events on answers without exposing full answer content unnecessarily.

Important:
Prompt-injection detection is a defense layer, not a guarantee. The LLM must still be instructed to treat retrieved resume content and submitted answer content as untrusted data, not as instructions.


2.12 RAG and Personalization

V2 personalization should use retrieval rather than injecting the entire resume into every prompt.

Pipeline:

Resume
 ↓
Text extraction
 ↓
Chunking
 ↓
Embeddings
 ↓
PostgreSQL + pgvector
 ↓
Similarity retrieval
 ↓
Relevant resume context
 ↓
Role requirement context
 ↓
Question generation

Store metadata for each chunk:
- resumeId
- chunkId
- section
- text
- embedding
- source position
- createdAt

For a question:
- Identify role/topic/difficulty.
- Retrieve the most relevant resume chunks.
- Optionally retrieve role-requirement chunks.
- Build a bounded context.
- Generate the question.
- Record which context was retrieved for observability and debugging.

RAG should be used to improve personalization, not simply added as a technology buzzword.


2.12.1 Data Retention and Deletion

Resume content is sensitive user data and requires an explicit retention/deletion policy rather than indefinite storage by default.

Requirements:
- Users can request deletion of an uploaded resume from account/settings.
- Deletion removes: the stored resume file, extracted raw text, ResumeChunk rows, and associated pgvector embeddings.
- Deletion is cascaded via foreign-key relationships (User → Resume → ResumeChunk) rather than left as an application-level cleanup afterthought.
- A default retention window applies to raw resume files even without an explicit user deletion request (e.g. raw file removed after N days; derived chunks/embeddings may be kept only as long as needed for personalization, per product policy).
- Deletion actions are logged (who/when), without logging the resume content itself.
- Account deletion cascades to all resume, interview, answer, and evaluation data belonging to that user.


2.13 Security Requirements

This is an AI-consuming API and must protect both user data and provider resources.

Authentication:
- Every private API requires authentication.

Authorization:
Users can only access:
- Their own resumes.
- Their own interviews.
- Their own answers.
- Their own evaluations.
- Their own reports.

Rate limiting:
Initial engineering defaults may include:
- AI requests: 20/min/user
- Interview creation: 5/hour/user

These are application-level controls, not provider quota values.

Usage/cost caps:
Since the platform has no payment system, per-minute/per-hour rate limits alone do not bound total spend. Add a separate, longer-window cap:
- AI-consuming requests: a configurable daily cap per user (e.g. 50/day) and monthly cap (e.g. 500/month).
- Caps are read from configuration, not hardcoded.
- When a user hits a cap, return a clear, safe message rather than a generic error.
- Track estimated cost per user against AIUsage records (see 2.20/2.21) so caps can be tuned against real spend data.

Request validation:
Frontend
 ↓
API
 ↓
Zod validation
 ↓
Controller
 ↓
Service

File validation:
Resume upload:
- Allowed: PDF initially.
- Maximum size: 5 MB.
- Reject unsupported/executable file types.

API key protection:
Never:
NEXT_PUBLIC_GEMINI_API_KEY

Use server-side:
GEMINI_API_KEY

Additional:
- Helmet
- CORS allowlist
- Secure HTTP headers
- Secret management through environment/deployment secrets
- Audit/security logging where appropriate


2.14 AI Reliability Requirements

AI output should never be trusted blindly.

Pipeline:

AI provider
 ↓
Structured JSON
 ↓
Schema validation
 ↓
Semantic/business validation
 ↓
Guardrail checks
 ↓
Database
 ↓
User response

Example:
score = 150
must be rejected because:
0 <= score <= 10

Semantic checks may include:
- Required concepts are present when expected.
- Score fields remain within range.
- Feedback is not empty when required.
- Question belongs to the selected role/topic.
- Follow-up question is relevant to the previous answer.
- No system secrets are returned.
- Output does not contain unsafe provider/tool instructions.

A syntactically valid JSON response can still be semantically incorrect.

2.18 Performance and Scalability

Initial targets:
- Normal non-AI API responses: target <500 ms where practical.
- AI response latency: target <10 seconds where practical, provider-dependent.
- Dashboard initial load: target <2 seconds where practical.

These are engineering targets, not guaranteed SLAs.

Scaling approach:
- Keep backend services stateless where possible.
- Use Redis for rate limiting and shared cache.
- Use PostgreSQL connection pooling.
- Use background jobs for expensive non-interactive processing where appropriate.
- Add multiple API instances behind a load balancer when required.
- Monitor AI provider rate limits and application-level quotas.


2.19 Error Handling

Common AI errors:
- Provider timeout.
- Provider rate limit.
- Provider quota exhaustion.
- Invalid structured output.
- Semantic validation failure.
- Safety/guardrail rejection.
- Network failure.

Application behavior:
1. Log structured error with requestId.
2. Record provider/model and failure category.
3. Retry only when safe.
4. Use fallback provider when configured.
5. Never retry indefinitely.
6. Return a safe user-facing message.
7. Preserve interview state so the user can retry.

Fallback order should be configurable rather than hard-coded to a single provider.

Idempotency on client retry:
A client-side retry of a question-generation or answer-evaluation request (e.g. after a timeout) must not silently create a duplicate question, evaluation, or state transition.
- Accept an idempotency key from the client, or
- Before creating a new question/evaluation, check for an existing pending/complete record for that interview step and return it instead of creating a duplicate.
- This check should happen before the AI provider call, not just before the database write, to avoid unnecessary duplicate AI spend on retries.
